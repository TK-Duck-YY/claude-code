# docx-reference-format

把一份 Word 文件的「文字外觀」與「頁面/圖表幾何」拆成兩個獨立來源分別處理，
避免常見的兩個事故：

1. 為了套用範本的字型字級，連帶把原始檔的圖表搬位、縮放，或誤改頁碼/頁首頁尾結構。
2. 為了保留原始檔版面，連帶把範本明確要求的字型字級/縮排規則也保留了原始檔的（沒套用到）。

這份 skill 涵蓋兩種情境，做法共用同一套角色分離原則，差別只在「基準是誰」：

- **情境A：單一範本套單一原始檔**——參考範本與原始檔是兩份不同性質的檔案（見下方角色定義）。
- **情境B：N份章節/檔案彼此必須完全一致**——例如同一本書的第1~7章，本來就應該長得一樣，
  其中一份（通常是使用者已經手動調到滿意、或最早/最權威的那份）當基準，其餘N-1份都要
  逐欄位比對到跟基準完全一致。這種情境下「基準」扮演參考範本的角色、「其餘每一份」各自
  扮演原始檔的角色（各自的圖表位置/大小/編號/頁面方向都要保留自己原本的，不能互相覆蓋）。

## 角色定義（絕對不可混用）

| 來源 | 決定什麼 | 絕對不能決定什麼 |
|---|---|---|
| **參考範本 / 基準檔**（reference） | 具名樣式的字型/字級/顏色/粗細/段落間距、項目符號與多層次清單的縮排與編號格式 | 圖表位置/大小、頁面方向、頁首頁尾結構 |
| **原始檔 / 其餘每一份要對齊的檔**（original，要被更新的檔） | 圖表在文件中的位置與大小、圖表編碼順序、各節頁面方向（橫向/直向）、頁首頁尾結構 | 文字外觀規則（除非範本沒定義，才用 fallback） |

任何時候如果發現某個格式設定「兩邊都可以决定」，停下來，不要猜——回報衝突給使用者（見下方「停止條件」）。

## 何時使用這個 skill

- 使用者要把舊文件「換新內容」但「外觀照舊範本」。
- 使用者要抽換圖片但圖表的位置/大小/編號不能跑掉。
- 使用者要把多份文件統一成同一套字型/字級/縮排規則，但每份文件本身的頁面方向/圖表配置不一樣，不能互相覆蓋。
- 使用者說「格式不統一」「全面稽核格式」「每一章都要跟第一章一樣」這類話，且明確或可推斷出哪一份該當基準。
- 使用者明確說「不要把橫向頁翻成直向」「不要動圖表」「字型照範本」這類話。
- 使用者已經修過幾輪症狀式的格式問題，但彼此之間還是有落差（這是情境B最典型的觸發點——
  每次只修「當時已知的症狀」，卻沒有做「逐欄位全量比對」，日積月累出「各自缺一塊、缺的還不一樣」的局面）。

不要在使用者只是要「修改某段文字」「填表」「轉換格式」（沒有牽涉到外觀比照另一份範本或基準）時觸發本 skill；那種情況直接用 docx 技能處理即可。

## 執行步驟

### 步驟 0：確認角色

情境A：跟使用者確認清楚「哪一份是參考範本（決定文字外觀）」「哪一份是原始檔（要被更新、且幾何要保留）」。
兩份檔名都帶「範本」或语意不明確時，**必須先問**，不要用檔名猜。這是最容易出錯也最難事後挽回的一步
（一旦角色搞反，圖表幾何會被誤改）。

情境B：跟使用者確認「哪一份當基準」（通常是使用者已經手動調到滿意、或最早/最權威的那份），
若使用者沒有明講但脈絡清楚（例如反覆用「第一章」當比對對象），可以推斷但要在動手前明確覆述
一次讓使用者確認，不要默默假設。

### 步驟 1：解壓並讀取基準檔的真實樣式定義

用 `scripts/apply_reference_format.py` 內建的解析函式（基於 `zipfile` + `lxml`，**不是**憑記憶中的 Word 預設值）：

- 讀取基準檔 `word/styles.xml`，抽取具名樣式（標題 1/標題 2/副標題/內文，依 `w:name w:val` 比對，
  同時容許英文別名 Heading 1/Heading 2/Title/Subtitle/Normal）的：
  `w:rFonts`（中文字型 `eastAsia`、英文數字字型 `ascii`）、`w:sz`（字級，半磅）、`w:color`、`w:b`（粗細）、
  `w:spacing`（段前/段後）。
- 讀取基準檔 `word/numbering.xml`，抽取每個有被使用的 `abstractNum` 在 `ilvl` 0–4 的：
  `numFmt`、`lvlText`（編號/符號格式）、層級文字的字型/字級/顏色/粗細、
  以及縮排 **`w:leftChars` / `w:firstLineChars`（單位：百分之一字元，即 100 = 1 字元）**。

凡基準檔沒有定義到的項目，套用 `references/format-defaults.md` 裡的 fallback 標準值，
並在驗證報告中標註「基準未定義，已套用 fallback」。

**情境B額外要做的事**：不要只鎖定「標題1~4/normal」這幾個看似核心的具名樣式。額外從
「目標檔內文段落實際引用了哪些 pStyle」反向掃描一次——逐段落讀出 `w:pPr/w:pStyle`，
統計每個 styleId 被多少段實際內文使用，特別留意任何**非normal/非heading、卻被大量
內文段落使用、且該樣式自己帶有明確 `w:rFonts` 的情況**：這種樣式往往是從別份文件貼上
殘留下來的（樣式名稱常常帶括號、或是「Note Heading」這類 Word 內建樣式被挪用改名），
只同步「五大核心樣式」完全抓不到這種問題（實案：某章節內文字體跟其他章不一樣，根因
不是核心樣式沒同步，而是該章內文段落被誤掛在一個寫死「標楷體」的殘留樣式上，同步
normal/heading完全無效，必須直接把該樣式的參照從段落上拔掉、回歸預設值）。

### 步驟 2：在目標檔裡，只改寫「具名樣式定義」與「多層次清單定義」本身

**不要**逐段落、逐文字框覆寫格式。改寫目標是目標檔 `word/styles.xml` 與 `word/numbering.xml`
裡同名具名樣式 / 清單定義的屬性值，讓全文套用具名樣式的段落自動套到新外觀。

這樣做的好處：完全不需要去碰 `document.xml` 裡的 `w:drawing`（圖表錨點）與 `w:sectPr`
（頁面方向/邊界），幾何自然不會被動到。

情境B下，每個目標檔要保留「自己原本的」清單編號識別碼（`numId`）：先讀出目標檔標題1
現有 `w:numPr/w:numId` 的值，複製基準檔的 `pPr`/`rPr` 過去後，只把 `numId` 欄位改回
目標檔原本的值（`ilvl` 沿用基準檔的 0/1/2/3），確保多層次清單的「檔案本地識別碼」不被
誤用成基準檔的（在其他檔案裡沒有意義甚至可能撞號，見下方「多層次清單三個雷」）。

若步驟1額外掃描發現段落被誤掛在殘留/非核心樣式上：把該段落的 `w:pStyle` 參照直接
拔除（回歸預設Normal），段落自己帶的 `w:numPr`（清單編號）、`w:jc`（對齊）等屬性維持
不動——只拔樣式參照，不動段落自己的其他格式設定。動手前先確認這些段落是否都在主文流
內（不在任何表格內），避免影響到表格儲存格自己的格式邏輯。

### 多層次清單（numbering.xml）三個已知的雷，複製/操作 abstractNum 時必查

1. **`w:abstractNumId`**：檔案本地索引，安全做法是取目標檔現有最大值+1。
2. **`w:lvl/w:pStyle`**：這個子元素會把某個清單層級自動連結到「同名styleId」的
   具名樣式——來源檔案的styleId數字在目標檔案裡可能完全對應到不相干的樣式，
   複製過去若不處理，會讓不該套用清單格式的段落意外變成清單。**複製任何
   abstractNum時一律移除所有`w:lvl`底下的`w:pStyle`子元素**（不需要這個自動
   連結功能，具名樣式本身的`w:numPr`已經明確指定要用哪個numId）。
3. **`w:nsid`**：這是Word用來偵測/合併「相關清單」的簽章（不是`w:tmpl`——`w:tmpl`
   查過沒用，兩者都是`w:abstractNum`的**子元素**、不是屬性，用`.find()`不是
   `.get()`，用`.get()`會靜默回傳None造成誤判）。複製abstractNum到目標檔案時，
   若目標檔案剛好已有另一條「不相關但nsid撞號」的舊abstractNum，Word會把兩者
   當成同一份清單合併顯示，套用錯的那份格式——症狀通常是「LibreOffice看起來
   正常，但Word裡標題編號變成`1./甲、/i.`這類意外符號」。修法：一律指派全新
   隨機nsid（`secrets.token_hex(4).upper()`），並檢查跟目標檔案現有全部nsid
   不撞號。

這三個雷曾各自單獨復發過，務必三個都處理，不要只處理其中一兩個就以為安全。

### `.rels` 檔案重寫的序列化陷阱（曾導致整份文件「無法載入」且無明確錯誤訊息）

若需要**從無到有**重新產生任何 `_rels/*.rels` 檔案（例如替換頁首/頁尾圖片後重寫
`headerN.xml.rels`），根元素務必用**預設命名空間**、不能帶前綴：

```python
from lxml import etree
REL_NS = 'http://schemas.openxmlformats.org/package/2006/relationships'
rel_root = etree.Element(f'{{{REL_NS}}}Relationships', nsmap={None: REL_NS})  # 正確
# 錯誤寫法：etree.Element(qn('rel:Relationships'))
# 這會讓lxml自動配一個`ns0:`前綴序列化成 <ns0:Relationships xmlns:ns0="...">，
# 雖然是合法XML、命名空間URI也對，但LibreOffice/Word的.rels part讀取器會拒絕
# 載入整份docx（"source file could not be loaded"），且python-docx開啟、
# zipfile.testzip()、lxml individual parse全部正常，只有實際用LibreOffice
# 轉檔或Word開啟才會發現。同套件裡其他`.rels`檔案（如document.xml.rels）都是
# 無前綴寫法，複製既有寫法風格最保險。
```

### 步驟 3：套用文件慣例（C 類，與基準/目標檔無關，一律套用）

讀 `references/format-defaults.md` 的「文件慣例」表，套用：

- **版面邊界**：只對**直向**的 `w:sectPr`（沒有 `w:pgSz w:orient` 屬性，或值為 `portrait`）套上
  上1.27／下1.44／左1.95／右1.27 公分；**橫向**的 `sectPr`（`w:orient="landscape"`）完全跳過，
  原始邊界一律保留，不可套用直向邊界、不可翻轉方向。
- **日期格式**：掃描內文（不含頁首頁尾）裡的日期文字（含民國年），轉換為西元 `YYYY/MM/DD`
  （月、日皆兩位數）。每一筆轉換都記錄到驗證報告供使用者覆核，避免把普通數字誤判成日期。
- **版次**：只檢查現有版次字串是否符合 `X.Y` 格式；**不要**自動判斷該不該跳大版號——
  這需要使用者對「改動幅度」的判斷，寫進驗證報告請使用者自行決定，必要時參考
  `references/format-defaults.md` 的版次規則指南。
- **頁碼／表單編號**：若目標檔頁尾已經有對應欄位，正規化其格式（`n/總頁數`）；
  **若頁尾原本沒有這些欄位，不要新增**——新增頁尾欄位等於更動頁首頁尾結構，違反角色定義裡
  「目標檔的頁首頁尾結構不可被更動」的硬規則。沒有欄位時只在報告標註「缺漏，待人工確認」。

### 步驟 4：依序抽換圖片（若使用者提供新圖檔）

依文件中圖表出現的順序（`w:drawing` 在 `document.xml` 中出現的順序）一一對應抽換，
只替換 `word/media/` 裡的圖片二進位內容，**不改** `wp:extent`（大小）、
不改該圖表在段落中的錨點位置、不改編號順序。若新圖與原圖長寬比差異超過 5%，
在驗證報告標註「長寬比不符，套用後可能變形，建議確認」。

情境B下若同時涉及頁首/頁尾圖片統一（例如某份檔案的頁首用了跟其他份不同的圖），
先用md5等雜湊比對確認其餘各份檔案的頁首/頁尾圖片是否本來就byte-for-byte相同，
再決定要不要重建；圖片複製過去後記得檢查舊圖片檔是否還被其他`.rels`引用，沒有
才刪除實體檔，避免留下懸空引用或誤刪還在用的圖。

### 交付前：重新staging紀律（避免用過時內容覆蓋使用者或自己先前的成果）

以下兩種情境都會導致「悄悄用到過時內容」，且**不會有任何錯誤訊息**，唯一能抓到的
方法是重新核對mtime/size或實際比對關鍵內容：

1. **使用者在Claude處理期間持續編輯同一批檔案**：任何跨越「使用者可能同時在編輯
   來源檔案」這段時間的任務，在真正組裝最終交付檔案前，務必重新抓一次即時版本，
   核對大小/mtime是否跟手上快取的版本一致，不一致就要用新版本重做。
2. **Claude自己前一輪的修復成果還沒有寫回使用者的檔案系統，後一輪任務又從舊快取
   重新複製出發**：同一次對話裡對同一個檔案有多個先後任務時，後一個任務應該接著
   前一個任務在本地已修改過的版本繼續改，而不是每個任務都重新從最初的來源複製，
   除非能先確認前一輪的成果已經確實寫回。

判斷是否要重新核對的簡單信號：檔案大小或mtime跟自己上次記錄的數字對不上，就是
被動過的鐵證。

### 步驟 5：輸出並自我驗證

跑完所有步驟後，輸出：
1. 更新後的 .docx
2. 驗證報告（Markdown），逐項比對「驗收標準」（見下方），每項標示 ✅/⚠️/❌ 與具體數值。

**最終驗收必須用真正的渲染引擎跑一次**（LibreOffice `--convert-to pdf` 或實際在
Word開啟），不能只做結構性檢查就結案。python-docx能開、`zipfile.testzip()`正常、
lxml能parse，都只驗證「合法的zip+合法的XML」，不保證Word/LibreOffice真的能載入
或渲染正確（見上方`.rels`序列化陷阱——結構檢查全部過關，但實際渲染直接失敗）。

情境B下，若這輪改動了標題/內文樣式的間距或縮排，即使沒有動到任何字數或圖片，
也要在交付前重新核對目錄（如果有的話）記載的頁碼是否跟實際分頁一致——間距/縮排
變化會讓後續內容的分頁往前或往後飄移，不能只驗證「樣式欄位是否一致」就結案。

## 驗收標準（驗證報告必須逐項列出）

- [ ] 標題1/標題2/副標題/內文的字型、字級、顏色、粗細與基準檔逐一相符（或註明用了 fallback）。
- [ ] 項目符號與五層縮排（1. / 1.1 / 1.1.1 / A. / a.）的縮排字元數與間距相符。
- [ ] 每張圖表的位置與大小與目標檔原本的完全相同。
- [ ] 各節版面方向（橫向/直向）與目標檔原本的相同；橫向頁未被翻轉或套錯邊界。
- [ ] 圖表編碼順序不變；抽換後位置、大小、編號維持。
- [ ] 日期格式、版次格式、頁碼 n/總頁數、表單編號的檢查結果（含未變動項目的原因）。
- [ ] 頁首頁尾結構是否被更動（必須是「否」）。
- [ ] （情境B）多份檔案的normal+標題1~4具名樣式pPr/rPr逐位元組比對後完全一致（numId正規化後）。
- [ ] （情境B）多份檔案的頁首/頁尾圖片md5比對後byte-for-byte相同（若適用）。
- [ ] （情境B）全部檔案都已用真正渲染引擎（LibreOffice/Word）驗證能正常載入與渲染。
- [ ] （情境B）若有目錄，目錄記載頁碼與實際分頁一致。

## 停止條件（動作前先問使用者，不要猜）

- 要刪除任何既有檔案前。
- 基準檔（文字外觀）與目標檔（頁面幾何）的設定彼此衝突、且會影響輸出結果時
  （例如範本本身內嵌了圖表，使用者卻把它當文字外觀來源——這時圖表幾何規則不適用於範本本身，
  但若使用者意圖不清，先問）。
- 同一個格式問題（例如某個縮排怎麼讀都讀不出正確的 leftChars 值）嘗試兩次仍無法解決時，
  停下來回報，不要硬套一個可能錯的值；同時把這個案例記錄到使用者的 ERRORS.md（若有）。
- 兩份輸入檔的角色（哪份是範本、哪份是原始檔）不明確時；情境B下哪一份當基準不明確時。
- 診斷「兩份文件同一種內容看起來不一樣」但原因不明時：**先鎖定使用者指出的具體那段
  文字，找到它在XML裡的確切段落與pStyle，再去看該樣式自己的定義**——不要先做「全文
  統計某個屬性有無」這種掃描再反推結論，容易比較到兩種不相關的內容（實案教訓：曾經
  統計run層級字型覆寫次數，抓到的是完全不相關的圖表框內文字樣式，跟使用者截圖裡的
  一般內文毫無關係，浪費一輪來回還下錯結論）。

## 已知限制 / 待真實檔案驗證的假設

- `w:leftChars`/`w:firstLineChars` 採用「100 = 1 字元」換算（OOXML 字元縮排單位慣例）；
  若實測發現與 Word 實際顯示效果不符，記錄到 ERRORS.md 並調整換算係數。
- 公分轉 twips 用 `twips = round(cm * 1440 / 2.54)`。
- 圖片抽換僅替換二進位內容，不主動轉檔；不同副檔名的新圖會嘗試用 Pillow 轉成與原圖相同格式，
  失敗則在報告中標註並保留原圖。
- 日期偵測為規則式（regex）比對民國年/西元年格式，非語意理解；非標準格式的日期可能漏判，
  漏判項目不會出現在報告中，使用者仍應自行檢查內文日期。
